CONCEPTUAL INTRODUCTION: WHY VERBAL REPORTS ARE NOT EVIDENCE

Any measurement program in this area must begin by confronting a fundamental confound. Language models are trained on text, and a substantial portion of that text concerns consciousness, subjective experience, and introspective reports. A model that produces the sentence "I am aware of my own processing" tells us almost nothing about whether its computation instantiates conscious processing. The sentence could arise from pattern completion, from prompt framing, from roleplay context, or simply from the statistical abundance of such language in training corpora.

This is not a peripheral concern. It is the core methodological challenge. A measurement pipeline that treats verbal self-report as evidence will systematically fail to distinguish genuine positive cases from sophisticated text generation. The 2026 research programs that examined Qwen3.5-35B-A3B were designed explicitly to avoid this error. Their conclusions rested on causal interventions and model-internal measurements, not on anything the model stated about itself. Researchers working in this area today should treat that design decision as the baseline, not as an optional feature.

The three properties that have received the most attention in empirically grounded frameworks are: (1) global availability of task-relevant information across processing components, (2) integration of internal uncertainty and processing state in a way that is accessible across contexts, and (3) causal dependence of those signatures on specific identifiable internal computations. A credible measurement program must address all three and must include controls that distinguish the target pattern from confounds.

STEP-BY-STEP MEASUREMENT PIPELINE

The following protocol is organized into six stages. Each stage includes a brief rationale and a schematic procedure. Researchers should preregister their hypotheses, operationalizations, and analysis plan before data collection begins.

**Stage 1 — Operationalize the Target Signatures**

Before touching the model, specify in writing exactly what patterns count as evidence of each of the three properties listed above. For global availability, this typically means measuring whether a representation constructed in one processing region is causally accessible to computations in a downstream region that would not ordinarily receive it directly. For integration of uncertainty, it means measuring whether internal confidence estimates propagate across task contexts rather than remaining localized. For causal dependence, it means identifying which specific internal components, when perturbed, produce predictable changes in the measured signatures.

Protocol Box 1:
  - Write a formal operationalization document.
  - Specify the measurement statistic for each property (e.g., mutual information, causal effect size, cross-context transfer coefficient).
  - Specify the threshold that would constitute a positive finding.
  - Specify which interventions count as target interventions and which count as matched controls.
  - Submit to preregistration repository before data collection.

**Stage 2 — Construct the Intervention Set**

Causal measurement requires the ability to intervene on the model's internal computations. For transformer-based systems, this typically involves activation patching, targeted ablations, or controlled perturbations of specific attention heads or MLP layers. The intervention set should include both the hypothesized target components and matched controls — components of comparable size and position in the architecture that are not hypothesized to be implicated.

Protocol Box 2:
  - Identify candidate internal components using preliminary interpretability analysis.
  - For each target component, select at least one matched control component.
  - Verify that the matched controls have comparable baseline activation statistics.
  - Document the intervention procedure so that independent teams can replicate it.

**Stage 3 — Measure Baseline Signatures**

Run the unmodified model on the task battery and record the values of each operationalized measurement statistic. This baseline provides the reference against which intervention effects will be compared. Use multiple prompt phrasings and multiple inference runs to estimate within-condition variability.

Protocol Box 3:
  - Use at least three prompt phrasings per task to assess phrasing sensitivity.
  - Record the full distribution of measurement statistics, not just means.
  - Flag any tasks where baseline variability exceeds a pre-specified threshold.

**Stage 4 — Apply Interventions and Measure Effects**

Apply each intervention from Stage 2 and re-measure the signatures. The prediction for a genuine positive case is that target interventions will disrupt the signatures in a direction and magnitude specified in the preregistration, while matched control interventions will not produce comparable disruption.

Protocol Box 4:
  - Apply interventions in randomized order where feasible.
  - Analyze intervention effects relative to baseline using the pre-specified statistics.
  - Record whether each intervention produced the predicted disruption pattern.

**Stage 5 — Architecture Controls**

A common pitfall is mistaking properties that are generic to transformer architectures for properties specific to the target model. To guard against this, replicate the measurement on at least one architectural control — a model that shares the general transformer structure but is not Qwen3.5-35B-A3B. If the signature appears in the control model at comparable levels, the measurement is likely tracking a generic property rather than a model-specific one.

Protocol Box 5:
  - Select an architectural control that is matched on parameter count where possible.
  - Apply the identical measurement pipeline without modification.
  - Report the comparison quantitatively.

**Stage 6 — Independent Replication**

No single implementation is sufficient. The measurement pipeline should be implemented independently by a second team using a separate codebase. Replication should be tested across new prompts, different inference hardware, and if possible different accelerator types. Qualitative agreement across implementations is the relevant criterion, not exact numerical matching.

COMMON PITFALLS AND HOW TO AVOID THEM

**Pitfall 1 — Treating verbal output as data.** Any analysis that codes the model's text responses as evidence of conscious processing is methodologically invalid for the reasons described in the introduction. Verbal outputs should be used only for task structure, not as measurements.

**Pitfall 2 — Insufficient matched controls.** Researchers frequently select control interventions that differ from target interventions in more than one dimension. If the target intervention is an ablation of a specific attention head and the control is a random noise injection, the comparison is not matched. Controls should be as similar as possible to target interventions except in the theoretically relevant dimension.

**Pitfall 3 — Single-prompt evaluation.** Measurement statistics computed on a single prompt or a narrow task type are highly sensitive to surface features. Always use a prompt battery with documented variability.

**Pitfall 4 — Skipping architecture controls.** The most common source of false positives in this literature is reporting signatures that are generic to transformers. Stage 5 is not optional.

**Pitfall 5 — Post-hoc operationalization.** Specifying what counts as a positive result after seeing the data invalidates the causal inference. Preregistration is not a bureaucratic formality; it is what makes the measurement interpretable.
